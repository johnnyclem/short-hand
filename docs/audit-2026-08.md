# Code Review & Security Audit — short-hand

**Date:** 2026-08-15
**Scope:** Full repository (`src/`, tooling, docs, CI)
**Method:** Manual read of all source files, dependency audit, test/lint/build verification.

## Summary

`short-hand` is a small, well-engineered TypeScript library (~7,000 LOC) implementing
progressive context compaction for LLM conversations, plus CRDT-based multi-agent
memory and a safety-bounded pluggable LLM interpreter layer. It has zero runtime
dependencies, strict TypeScript, and 153 passing tests with deliberate, tested safety
boundaries around the one place it talks to an LLM (`ActiveEngramStore` /
`Interpreter`). The codebase is unusually clean for its size — this audit found no
critical application-logic vulnerabilities and made surgical, non-breaking fixes
rather than a large-scale rewrite.

Because this is a library (not a hosted service), the traditional web/API attack
surface (auth, endpoints, rate limiting, CSRF/XSS at a UI layer) does not apply
directly — those concerns belong to host applications that embed this package.
The audit focused on what *is* in scope for a library: dependency/toolchain
hygiene, correctness of security-relevant contracts (the interpreter boundary),
data-handling safety in CRDT merges, and process gaps (CI).

## Findings

### High

**H1 — No CI pipeline existed.** The repository had no `.github/workflows/` (or
any other CI config), despite `docs/qa-engineering.md` explicitly documenting CI
behavior ("CI runs without an API key", live tests skip via
`it.skipIf(!process.env.ANTHROPIC_API_KEY)`). With 153 passing tests and clean
typechecking already in place, nothing enforced them on pushes or PRs.
**Fixed:** added `.github/workflows/ci.yml` running `npm run lint`, `npm test`,
and `npm run build` on push to `main` and on every PR, across Node 18/20/22
(the package's declared `engines.node` floor plus current LTS/latest).

**H2 — Critical/high vulnerabilities in the dev toolchain.** `npm audit` reported
5 vulnerabilities (1 low, 3 high, 1 critical), all in the `vitest` dependency
chain (`vitest` <3.2.6, `esbuild`, `vite`, `nanoid`, `postcss`). These are
**devDependencies only** — the published package (`files: dist, LICENSE, README`,
zero runtime deps) ships none of them, so there is no supply-chain exposure for
consumers of `short-hand`. The exposure was to local development and CI
(e.g. esbuild's dev-server arbitrary file read, nanoid's DoS via crafted size,
postcss's path traversal via `sourceMappingURL`).
**Fixed:** `npm audit fix` resolved all 5 within the existing `^3.1.1` semver
range for `vitest` (landed on 3.2.7); `package.json` itself required no change.
Verified 0 vulnerabilities post-fix; full test/lint/build suite still green.

### Medium

**M1 — Dead/misleading invariant check.** `InvariantChecker.checkTombstoneConsistency`
(`src/verification/invariant-checker.ts`) declared a `violations` array and an
`if` branch containing only a comment — the branch never executed any logic and
the function unconditionally returned `passed: true`, ignoring the array
entirely. This audit independently flagged and fixed it, but by the time this
branch was rebased onto `main`, PR #10 ("code review cleanup") had already
landed a more thorough fix — the check now validates that every tombstone has
a `correctionMessageId` and a `reason`, and fails the check (rather than just
warning) when either is missing. This branch's redundant fix was dropped in
favor of the already-merged one; no further action needed here.

**M2 — Non-collision-resistant ID generation.** `generateId()`
(`src/utils.ts`) combines `Date.now()` and `Math.random()`. It is not
security-sensitive today (used for message/engram/summary IDs, never for
auth tokens or secrets), but IDs are used as `Map` keys throughout
(`ActiveEngramStore.add`, L2 summary IDs, etc.) — a collision would silently
overwrite an existing entry rather than error.
**Fixed:** documented the tradeoff directly on the function so a future
caller relying on it for anything collision-sensitive knows to swap it out;
left the implementation unchanged (no observed use case today justifies a
breaking behavior/API change).

**M3 — Unvalidated, host-configurable HTTP endpoint in `LocalInterpreter`.**
`LocalInterpreter` posts to a caller-supplied `endpoint` string (default
`http://localhost:11434/api/generate`) with no scheme/host validation. This is
by design — it's a constructor option for the host application, not something
this library parses from untrusted input — but a host application that ever
threads user-controlled input into that option would create an SSRF vector.
**Fixed:** documented the trust assumption on the option itself.

### Low / Positive Observations

- **No prototype-pollution risk in CRDT merges.** `LWWRegister`, `ORSet`, and
  `GSet` all deserialize into `Map`s, not plain objects, so merging untrusted
  serialized state cannot pollute prototypes. Good defensive design choice,
  no action needed.
- **No secrets or credentials found** in the repository; `.npmignore` and the
  `package.json` `files` allowlist correctly restrict the published package to
  `dist/`, `LICENSE`, and `README.md`.
- **Regex-heavy hot paths** (`RegexCompactor`, `RecallTester`,
  `ImportanceDetector`) use lazy quantifiers without nested repetition — no
  classic catastrophic-backtracking (ReDoS) pattern was found. There's no
  explicit length guard before scanning at the `CompactionEngine.addMessage`
  boundary, though `SourceIngester` already chunks documents to ~800 tokens
  before they reach it. Noted as a resilience consideration for host apps that
  call `addMessage` directly with unbounded content, not a confirmed
  vulnerability — no change made.
- **The interpreter/engram safety boundary is genuinely well-built.**
  `importanceScore` mutation is gated to a single method
  (`ActiveEngramStore.setImportance`), and every `Interpreter` implementation
  is tested to receive only `{template, payload, context}` on the wire — this
  is exactly the kind of "structural, tested boundary" that's easy to get
  wrong and this codebase gets right, including a maintainer-facing checklist
  in `docs/qa-engineering.md`.

## Remaining Technical Debt / Recommended Next Steps

1. **Tier 1/2 compactors are stubbed.** `CompactionEngine.resolveCompactor()`
   falls back to regex for `'local'`/`'host'` tiers today — this is documented
   in the README's "Compactor Tiers" table as "Planned," so it's expected, not
   a bug. No action needed unless/until those tiers are implemented.
2. Consider an explicit content-length guard (or documented recommendation) at
   `CompactionEngine.addMessage`/`addMessages` for host applications that don't
   route through `SourceIngester`'s chunking.
3. Consider bumping `generateId()` to something collision-resistant
   (e.g. a monotonic counter + random suffix, or `crypto.randomUUID()`) if a
   future feature starts treating engram/message IDs as anything more than
   opaque keys.
4. The new CI workflow runs on Node 18/20/22; revisit the matrix if the
   `engines.node` floor in `package.json` ever changes.
